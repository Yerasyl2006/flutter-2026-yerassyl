# Practice 11 — A Real Server

## 1. Что вернул JSONPlaceholder

Запросы выполнены через `curl` 11 ноября 2026 года. Content-Type всех пяти ответов — `application/json; charset=utf-8`.

| Запрос | HTTP | Тело ответа |
| --- | ---: | --- |
| `GET /users` | 200 | Массив из 10 пользователей с ID от 1 до 10 |
| `GET /users/1` | 200 | Один объект, Leanne Graham, ID 1 |
| `GET /users/999` | 404 | Пустой JSON-объект `{}` |
| `GET /users?id=3` | 200 | Массив из одного объекта, Clementine Bauch, ID 3 |
| `POST /users` | 201 | Сервер вернул переданные поля и назначил `id: 11` |

Для POST отправлены `name`, `username`, `email` с заголовком `Content-Type: application/json`. Отдельно проверен POST полного объекта с `id: 0` — сервер заменил его на `11`. JSONPlaceholder имитирует запись, поэтому созданные в приложении записи хранятся в памяти до его перезапуска. Фильтр передаётся третьим аргументом `Uri.https(host, '/users', {'id': '3'})`.

## 2. Модели и преобразование JSON

`User.fromJson` использует вложенные `Address.fromJson` и `Geo.fromJson`. В отдельных пробах с реальным JSON анализ типов воспроизвёл ошибки при приведении широты к double и строкового ID к int. Координаты приходят строками, например `"-37.3159"`, поэтому `as double` завершится ошибкой типов. `double.parse` переводит строку в число. При `toJson()` координаты снова записываются строками, причём числовое значение сохраняется, а незначащие нули могут исчезнуть. Значение ID должно быть целым числом. Строка `"1"` вызывает `TypeError`. Телефон хранится как пришёл. Геттер `phoneDigits` удаляет все символы, кроме цифр и плюса. Сравнение и хеш пользователя определяются по ID.

`companyBs` сохраняет поле `bs` из ответа сервера. Благодаря ему сериализация сохраняет полную структуру `company`, а record остаётся двухполевым, как в задании.

## 3. HTTP и ошибки

`ApiClient` отправляет запросы через внедрённый `http.Client` и проверяет статус перед декодированием. Это важно для `404` — тело `{}` является корректным JSON, но причина ошибки уже известна из статуса. При сетевой ошибке или таймауте клиент выдаёт `NoConnectionException`. Таймаут применяется к получению полного ответа, включая тело. По истечении десяти секунд клиент отменяет запрос. `401` и `403` означают `UnauthorizedException`, `404` — `NotFoundException`, `5xx` — `ServerException`. Ошибка декодирования или несовместимая структура превращается в `BadResponseException`.

`UserRepository` возвращает только `User` или `List<User>`. Прямой импорт `package:http` есть в `api_client.dart` и `user_repository.dart`. В задании пример с прямым вызовом `http.Client()` в `main.dart` потребовал бы третий импорт. Поэтому точка входа вызывает `UserRepository.live()`, а фабрика создаёт HTTP-клиент.

## 4. Состояние и интерфейс

`UsersModel` вызывает репозиторий, хранит состояние загрузки и уведомляет экран через `ChangeNotifier`. Экран подписывается через `context.watch`. Исчерпывающий `switch` обрабатывает все варианты `ApiException?`. В отдельной пробе удаление ветки `BadResponseException` дало диагностическую ошибку `non_exhaustive_switch_expression`. `Retry` и жест обновления запускают `load()`.

Форма проверяет имя, логин и email. Кнопка Save блокируется до завершения POST, а модель дополнительно проверяет флаг сохранения. При `201` модель вставляет возвращённого пользователя с ID сервера в начало списка, а экран формы закрывается. При ошибке форма остаётся открытой и показывает SnackBar. Локально добавленные пользователи сохраняются при обновлении списка, поскольку публичный API имитирует запись.

## 5. Проверка сети

Проверки Flutter: анализатор выдал "No issues found!", все четыре теста прошли. Виджет-тест подтвердил переход в Offline при ошибке сокета и через 10 секунд виртуального времени при зависании. Отдельная проверка с реальным таймером и локальным TCP-сервером, который принимал соединение и не отвечал на TLS, заняла 10 008 мс. Через тот же репозиторий напрямую проверены 10 пользователей, обработка 404 и POST с id 11.

Оба сценария должны приводить к экрану «No network connection.» с кнопкой Retry. Точный момент ответа в режиме полёта зависит от того, когда ОС сообщит об ошибке. При зависшем запросе приложение использует собственный дедлайн в десять секунд.
